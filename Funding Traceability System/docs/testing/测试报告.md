## 五、安全测试结论

- 注入类：`keyword`、`reason`、`virtualId`、二维码 `code` 传入 SQL / XSS payload 均未触发异常或回显，响应为业务码或 404，无堆栈泄露（S-01～S-05、S-10～S-12）。
- 字段白名单：`fieldScope` 含 `password` 等非白名单字段返回 400（S-06）。
- 公开核验最小化：`/api/public/verify` 仅返回业务单号、金额、状态、四节点时间等 8 个公开字段，不含姓名 / 手机号 / 身份证号（S-13）。
- Token 安全：篡改 Payload 角色、缺少 `Bearer` 前缀、伪造会话凭证均返回 401（S-14～S-16）。
- 已记录低危风险 R-01（异常信息含 Java 类型名）、R-03（Demo 密码明文）、R-04（账号枚举）、R-05（无 Token 吊销），详见 `测试用例文档.md` 第八节。

### 6.5 瓶颈分析与优化建议

1. **Tomcat 工作线程 300 < 并发 500**：`application-test.yml` 设置 `max=300`、`accept-count=200`，约 200 个请求在连接队列等待，是申请提交 P90 达 2.4s 的主因。
2. **业务连接池 60**：2500 次申请写入集中在约 11s 内，HikariCP 连接获取与 MySQL 单行 INSERT 形成排队。
3. **申请提交为同步写库**：`apply()` 需先按 `virtual_id` 查学生再 INSERT，500 并发下可考虑异步落库 / 批量写入。
4. **压测客户端与服务端同机**：JMeter 自身线程与 GC 占用 CPU / 内存，结果偏保守；生产独立部署后指标会更好。
5. 本次压测已关闭 MyBatis SQL 控制台打印（`funding.mybatis.stdout-sql-log=false`），避免日志 I/O 干扰。

建议：将 Tomcat `max` 提升至 600～800、连接池提升至 100，并为 `privacy_access_apply.applicant_id / status` 增加索引后复测；溯源查询已满足 500ms 目标，无需调整。

## 九、总体结论

1. **功能测试**：核心业务（登录、资金流水全状态机、隐私调取两级审批、扫码溯源、导出）全部通过。
2. **权限测试**：横向 / 纵向越权、字段级隔离、两级审批越权、强制脱敏均被正确拦截，B-01 / B-02 修复有效。
3. **安全测试**：注入、Token 篡改、非法参数、二维码伪造 / 枚举均未突破，公开核验满足隐私最小化要求。
4. **性能测试**：500 并发下 0 错误、0 崩溃，总 TPS 452.9；溯源查询达标，申请提交平均 1.33s 未达 1s 目标，需按第 6.5 节优化后复测。
5. **数据隔离**：全程仅使用 `funding_test` / `funding_privacy_test`，压测前重置基线、压测后清理压测数据，未触碰演示库。

**测试结论：功能、权限、安全测试通过；性能测试满足稳定性与错误率要求，申请提交接口存在可优化的容量瓶颈。**
