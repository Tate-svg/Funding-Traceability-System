# 第二轮改进：评分快照、资助单关联、只读审计

基于第一轮评分完整性和隐私空闲会话修复继续实现。当前验证状态：后端97项测试通过，0失败、0错误、0跳过；前端8项逻辑测试、改动文件ESLint及生产构建通过。独立MySQL旧库迁移连续执行两次通过，3条旧评分总分及未留存状态保持不变，新库初始化通过。第一轮21项及新增62项真实MySQL/API专项通过。新增专项包括快照独立于当前规则、资助关系匹配与查询隔离、旧数据保留、只读写接口拦截及旧JWT按当前角色授权。完整浏览器和Windows本机回归尚未完成，不能把提交视为上线验收。

## 已实现的行为

1. 新评分由服务端保存指标名称、权重、规则摘要和留存时间。客户端提交的权重、名称、总分及规则摘要不作为计算依据。编辑已留存规则的评分继续按该快照计算，不受当前指标修改或删除影响。
2. 新增评分必须选择资助单，服务端核对学生、资助人是否匹配。评分列表可按fundId筛选，单据详情可查关联阶段评分。已关联评分的资助单不能改写申请资料或删除，避免破坏关联。
3. 旧评分不推测关联资助单，不回填未经留存的权重。详情和导出标记历史规则未留存；允许补充资助单关联及备注，调整得分须新建评分。
4. 新增AUDITOR只读审计角色及独立页面，只展示资助台账、评分及其快照、节点台账、操作日志的必要字段。原始日志参数、自由文本备注及隐私档案不在该接口中返回。
5. 只读审计角色由后端限制接口范围，业务写请求及旧隐私/管理接口均被拒绝；保留查询本人登录信息与登出。现有SUPERVISOR监事继续承担抽检、复核和隐私终审。每次认证按数据库当前角色授权，账号降为只读后旧JWT不能保留写权限，删除账号后旧JWT失效。

## 现有数据库升级

先备份现有业务库，在MySQL客户端选中业务库，再执行：

`backend/src/main/resources/sql/alter_score_snapshot_fund_auditor.sql`

这是增量迁移，不删除现有表或记录；允许重复执行，不创建固定密码用户。不要在现有数据库运行schema.sql或init_test_db.sql，它们是新库初始化脚本。迁移后同时更新前后端并重启后端加载新权限。

需要新增的字段为score.fund_id、score.rule_version、score.rule_captured_at、score_detail.item_name_snapshot及score_detail.weight_snapshot；增加资助单索引及AUDITOR的audit:readonly权限。

审核管理员在“用户管理→新增用户”中选择“只读审计”并设置账号密码。新账号登录后进入只读审计页面，不能代替监事完成抽检、复核或终审。

## 边界

规则摘要用于标识评分时保存的配置，不是专家AHP权重，也不是独立的规则发布审批系统。历史未知规则不自动还原，不支持“不适用”或部分指标评分。节点核验仍是本地时间记录与元数据哈希链，不包含第三方可信时间戳、离线核验、文件内容重新核验或绝对不可篡改承诺。

本轮增加了按数据库当前角色认证的查询开销，尚未重新测试性能，不能沿用旧性能数据宣称本轮已达到同样指标。
